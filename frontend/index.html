Checks supplier XML invoices with deterministic rules, marks the failing lines, and adds an experimental ML risk score.

Pick a sample or drop in your own file. Five rules label it VALID, INVALID or REQUIRES_REVIEW once the nested XML is parsed safely and flattened, and the transaction ID and amount are found wherever they sit. A small Random Forest adds a risk score, and every check is written to a JSON Lines audit log.

Synthetic data The demo starts from 400 generated invoices, and the risk model is trained on them. Please don't upload real invoices.

How it works

Pick a sample to watch it run.

  2. Validate Five deterministic rules decide the status and point at lines
  3. Score Experimental Random Forest risk score from eight validation signals
  4. Log One JSON line per file in the rotating audit log

About SupplyTrace

A portfolio project by Vishnu Jayanth: a small, honest version of the checks an accounts-payable system runs on supplier invoice files, built to be read end to end.

The problem

Companies exchange invoices as structured XML files: the supplier's billing system sends a file, and the buyer's accounts-payable system books it. A file that is missing its transaction ID, or carries an amount like 12,50.00, does not always fail on arrival. It can move through import jobs and queues and fail in a system several steps away, where the error no longer points to the file. SupplyTrace moves the check to the front door: it reads each file once, applies explicit rules, and shows the line that is wrong.

Design decisions

Rules decide, the model advises.
The status comes from five deterministic rules that anyone can read and test. The risk score sits next to it but never changes it, because the model is trained on simulated outcomes.
Untrusted XML is parsed defensively.
defusedxml refuses DTDs, so there is no entity expansion and no external entities. Documents nested more than 100 levels deep are rejected, and uploads over 1 MB get a 413 before the body is read.
Uploads are not stored.
Files are parsed in memory. Only a one-line summary (file name, transaction ID, status, reasons, risk score, size) goes to the audit log.
One pipeline for every entry point.
A single check, a batch and the streamed batch call the same function, so a file gets the same answer either way. Tests compare them.
Findings point at lines.
ElementTree does not keep line numbers, so after the safe parse a lightweight expat pass records them. Every rule in the checklist carries the line the page highlights.
The score explains itself.
Each tree's path is followed and every split's change in failure rate is credited to its feature, so the base rate plus the contributions adds up to the score.
Plain files over infrastructure.
Batch results are a CSV and the audit log is a JSON Lines file: easy to inspect, enough for a demo, and simple to swap for a database later.
Reproducible data.
The synthetic invoices come from a fixed seed, so the dataset, the model and the model card come out the same on every run.

Limitations

  • The risk model is trained on synthetic invoices with simulated outcomes. It says nothing about real suppliers.
  • Five rules only: no checks on line totals, tax, dates, currencies or duplicate invoices.
  • Repeated elements, such as several invoice lines, collapse to the last one when flattened, and XML attributes are ignored.
  • The audit log is one shared file on a temporary disk: every visitor sees the same log, and it resets when the hosted demo restarts.
  • No accounts or authentication. It is a demo, not a multi-user service.
